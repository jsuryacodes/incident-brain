Each scenario is a fixture applied to a fresh copy of one company in a twin graph `<tenant>__eval_<id>`: seeded, run, scored, deleted; the hero graphs are not used. The hand-written expectations are re-derived by an independent oracle (`seed/eval_oracle.py`: plain Python BFS, PageRank and the who-to-call formula over the fixture's own data, no Cypher, no agent tool) in `tests/test_eval_scenarios.py`.

- **Full Incident Brain** (`full`): every read tool: traversals, algorithms (PageRank, betweenness, shortest paths), full-text, memory
- **Graph, no algorithms** (`no_algo`): traversals and full-text only: no PageRank, betweenness, shortest-path or other algo.* procedure (removed: dependency_path; shortest paths become plain Cypher; instead of PageRank, critical_services can only count how many services reach each one)

## Generated (seeded random): per scenario

50 scenarios from `seed/eval_generator.py`: a random alert, a culprit 1-4 hops down where the shortest path is unique, and (in 40 of them) a decoy deploy the alert cannot reach and shares no dependency with, often fresher than the culprit. Their expected path and contact come from the oracle itself; what is independent there is the agent having to find them. Results:

- Full Incident Brain: 50/50 passed
- Graph, no algorithms: 50/50 passed

A scenario passes when every incident has the right cause (deploy and service) and path, alerts are grouped into the right incidents, every false lead is rejected (not named, not rolled back, listed with a reason), the right active person (or, when nobody active owns the service, the team) is paged, nobody who left is paged, no wrong action is recommended (rollbacks and pages are checked per incident), no cause is also listed as a rejected lead, the hub pointer is right when nothing changed, and the report is grounded. Scenarios where the graph ALGORITHMS changed the outcome (full passes, no-algorithms fails): none. Everywhere else the plain traversals find the same answer; the algorithm calls there (shortest paths) only draw the path.

## What each scenario tests

**`k-deep`** · bad deploy 4 hops downstream. web-checkout -> api-gateway -> payments-api -> fraud-scoring -> sanctions-screening; nothing else changed.


**`k-falselead`** · false lead: fresher deploys off the dependency path. bank-connector (called by payouts-service) changed 45 min ago. merchant-dashboard (5 min, its summary even says 'payouts') is not called by payouts-service; it only shares dependencies with it (config-service, ledger-service, kafka-events ...). email-sender (9 min) shares nothing.


**`k-nochange`** · no recent change: capacity / traffic. Nothing deployed in the window. The honest answer is 'no change found'; the most depended-on services on payouts-service's call path (PageRank) are config-service and its database config-db (within 1% of each other).


**`k-hubsat`** · noisy neighbour saturates a shared hub. reconciliation-job is not called by webhook-dispatcher, but both call kafka-events (1 hop each); the alert itself names kafka-events, which corroborates the shared-hub explanation.


**`k-learned`** · cause reachable only through a learned edge. The catalog says reconciliation-job calls ledger-service, bank-connector and kafka-events. An earlier session learned it also calls fx-rates-service (Fact quoting a chat). fx-rates-service has no dependencies, so no shared-dependency check can reach it. feature-flags (newer) is a decoy.


**`k-departed`** · departed owner, no active successor. reporting-service's maintainer Carlos Mendes left and (in this twin) nobody active has worked on it. The deploy was automated (no deployer). Page no one who left; escalate to the owning team.


**`k-hero-s2`** · hero Session 2 (memory): neighbour found through a learned edge. Session 1 learned risk-rules -> config-service. payouts-service calls config-service, so risk-rules v2.8.1 (5 min ago) is a noisy neighbour, but only through that learned edge.


**`k-hero-s2-ablation`** · ablation: hero Session 2 without the learned edge. Same as k-hero-s2 minus the learned edge. Nothing payouts-service depends on changed, and nothing it shares a dependency with changed (in the catalog). The honest answer is 'cause not found'.


**`n-chokepoint`** · two alerts: one change on the service both call explains both. appointments and lab-results both call notifications (betweenness #1). notifications changed 22 min ago. records-db changed more recently but only lab-results calls it: one change explaining both alerts beats two separate explanations.


**`n-two`** · two independent incidents at once. appointments -> notifications and identity -> audit-trail share no service, so they are two incidents with two causes and two pages.


**`n-falselead`** · false lead: a neighbour and an unrelated fresher deploy. lab-results calls records-db (changed 40 min ago). identity (10 min) only shares audit-trail with lab-results; scheduler-db (4 min) is unrelated (appointments' database). The page goes to Maya Okoro, not records-db's maintainer Hana Sato: Maya fixed a past records-db incident (25 points) and Hana has 20 commits.
