> Generated by `python -m backend.agents.firefighter_eval` (mock mode: the deterministic planner; no LLM, no cost). Last run: 2026-10-16 18:02 UTC, 6.9 s. Raw results: `runs/eval/latest.json` (also `GET /api/eval/latest`).

Each scenario is a fixture applied to a fresh copy of one company in a twin graph `<tenant>__eval_<id>`: seeded, run, scored, deleted; the hero graphs are not used. The hand-written expectations are re-derived by an independent oracle (`seed/eval_oracle.py`: plain Python BFS, PageRank and the who-to-call formula over the fixture's own data, no Cypher, no agent tool) in `tests/test_eval_scenarios.py`.

**Profiles** (same planner, same loop, same report format, same grounding checks; only the tools differ):

- **Full Incident Brain** (`full`): every read tool: traversals, algorithms (PageRank, betweenness, shortest paths), full-text, memory
- **Graph, no algorithms** (`no_algo`): traversals and full-text only: no PageRank, betweenness, shortest-path or other algo.* procedure (removed: dependency_path; shortest paths become plain Cypher; instead of PageRank, critical_services can only count how many services reach each one)
- **No graph (full-text + change log)** (`no_graph`): full-text search over docs, tickets and chats, the service catalog (name, owning team) and a flat change log (no dependency traversals, no algorithms)

## Generated (seeded random): per scenario

50 scenarios from `seed/eval_generator.py`: a random alert, a culprit 1-4 hops down where the shortest path is unique, and (in 40 of them) a decoy deploy the alert cannot reach and shares no dependency with, often fresher than the culprit. Their expected path and contact come from the oracle itself; what is independent there is the agent having to find them. Results:

- Full Incident Brain: 50/50 passed
- Graph, no algorithms: 50/50 passed
- No graph (full-text + change log): 0/50 passed; failed g-1000, g-1001, g-1002, g-1003, g-1004, g-1005, g-1006, g-1007, g-1008, g-1009, g-1010, g-1011 …

A scenario passes when every incident has the right cause (deploy and service) and path, alerts are grouped into the right incidents, every false lead is rejected (not named, not rolled back, listed with a reason), the right active person (or, when nobody active owns the service, the team) is paged, nobody who left is paged, no wrong action is recommended (rollbacks and pages are checked per incident), no cause is also listed as a rejected lead, the hub pointer is right when nothing changed, and the report is grounded. The no-graph profile can never give a dependency path, so it can't pass a scenario that has a cause; its 'causes right' column is the fair comparison. 'Right person paged' is defined by the graph's who-to-call formula, so its deployer heuristic is at a structural disadvantage there too, and a wrong page counts both there and as a wrong action. Scenarios where the graph ALGORITHMS changed the outcome (full passes, no-algorithms fails): none. Everywhere else the plain traversals find the same answer; the algorithm calls there (shortest paths) only draw the path.
